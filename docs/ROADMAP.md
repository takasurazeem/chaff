# Chaff Roadmap — Execution Order

This is the *execution* order, which is deliberately not the same as the issue numbering
and not the same as the phase grouping. It is ordered by **dependency**, **risk**, and
**what protects other work**.

Board: <https://github.com/users/takasurazeem/projects/9> · Repo: <https://github.com/takasurazeem/chaff>

---

## The insight that sets the order

**The scoring model is independently testable right now, before the catalog exists.**

Most of Phase 1 is a chain: catalog → indexer → thumbnails → UI. But the focus metric —
the highest-risk, highest-value part of the whole product — needs only two things: a way
to load pixels, and images whose properties are already known. Both of those exist today
(`fixtures/synthetic/`, generated by `tools/fixtures/generate_synthetic.py`).

So the scoring work does not have to wait behind the plumbing. Given that it is also the
part most likely to be *wrong in a way that destroys trust* (marking intentional bokeh as
blur), it should start as early as possible so there is the most time to iterate on it.

That is why Wave 2 below runs **in parallel with** Wave 1 rather than after it.

## Wave 0 — Make the loop verifiable

**Why first:** everything after this is guarded by it, and it is cheap. Right now tests
pass on exactly one machine; a cross-platform claim with one platform of evidence is not
a claim.

| Issue | Title | Why here |
|---|---|---|

## Wave 2 — Scoring (start immediately, in parallel with Wave 1)

**Why here:** highest risk, highest value, independently testable, and the thing the
product is actually for. Ordered so that each step is verifiable against a fixture that
already exists.

| Issue | Title | Fixture that proves it |
|---|---|---|
| [#11](https://github.com/takasurazeem/chaff/issues/11) | Focus metric: subject ROI, multi-scale, contrast-normalised | `bokeh_portrait`, `flat_low_contrast` |
| [#14](https://github.com/takasurazeem/chaff/issues/14) | Noise estimation, ISO-normalised | `noise_high_iso` |
| [#12](https://github.com/takasurazeem/chaff/issues/12) | Motion-vs-defocus via edge anisotropy | `blur_motion` vs `blur_defocus_*` |
| [#13](https://github.com/takasurazeem/chaff/issues/13) | Exposure clipping from RAW black/white points | `exposure_over`, `exposure_under` |
| [#15](https://github.com/takasurazeem/chaff/issues/15) | Shoot-relative percentile normalisation | needs a shoot, not a single frame |
| [#16](https://github.com/takasurazeem/chaff/issues/16) | Composite scoring, presets, tunable weights | #11–#15 |
| [#17](https://github.com/takasurazeem/chaff/issues/17) | Explainability: reason strings | #16 |

**Ordering inside the wave matters:** #11 and #14 land together. Laplacian variance is
*confounded by noise* — sensor noise is high-frequency energy, so a naive focus metric
scores a noisy-but-sharp frame as sharper than a clean one. The fix is to estimate the
noise floor and subtract its expected contribution. Splitting #11 from #14 would bake in
the bug and then require unpicking it.

**Exit gate for the wave:** the ordering assertions in `focus.rs` hold —
`sharp > blur_defocus_mild > blur_defocus_heavy`, and `bokeh_portrait` scores **sharp**
under ROI scoring while scoring *blurry* under whole-frame scoring. That second assertion
is the single most important test in the project.

## Wave 4 — Safety, before any delete button exists

**Why here — and why not later:** `reject` is a flag, so the product is fully usable for
culling *without* any file movement. That means safety can wait until now without blocking
anything. But it must be complete before a delete control is ever rendered, and it is the
highest-consequence code in the repo, so it gets its own wave and its own review.

| Issue | Title | Why this order |
|---|---|---|
| [#30](https://github.com/takasurazeem/chaff/issues/30) | Refusal rules for dangerous paths | Pure logic, no dependencies, zero risk of data loss — do the safe part first |
| [#31](https://github.com/takasurazeem/chaff/issues/31) | Pre-move re-hash + transactional commit | Must exist before anything can move |
| [#27](https://github.com/takasurazeem/chaff/issues/27) | Two-phase trash + fsynced JSONL manifest | The move itself |
| [#28](https://github.com/takasurazeem/chaff/issues/28) | Restore with hash verification | The undo path, proven before the delete path ships |
| [#32](https://github.com/takasurazeem/chaff/issues/32) | Purge + receipt — the only unlink call site | Last, and deliberately isolated |
| [#29](https://github.com/takasurazeem/chaff/issues/29) | Paired-delete resolution + warning UI | Only once all of the above are green |

**Exit gate:** a test that moves a synthetic pair to trash and restores it byte-identically,
run on all three platforms, plus a test asserting `unlink` appears in exactly one module.

## Blocked

[#40](https://github.com/takasurazeem/chaff/issues/40) is blocked on four things I cannot
guess:

1. SSH **username** for the build host (the host entry exists; I have a key; no user)
2. Linux **distro and version**, and **CPU architecture** (`uname -m`)
3. Permission to install Tauri's Linux build dependencies on that server
   (`libwebkit2gtk-4.1-dev`, `libgtk-3-dev`, `libayatana-appindicator3-dev`,
   `librsvg2-dev`, `build-essential`) — this modifies their machine
4. Confirmation of the boundary: **the deployed app never scans a folder the user has not
   explicitly chosen. No default library path, ever.**

## What "done" means for a wave

A wave is done when:

- its tests pass on all three platforms in CI,
- the relevant fixtures assert the *ordering and discrimination* properties, not magic
  numbers,
- anything user-visible has been **handed to the user for validation** — the harness
  builds, installs, launches and reads logs, and stops there,
- the issue is closed with the evidence in the closing comment.
